**Задача:** оценка вероятности мошенничества онлайн-транзакции.  
**Источник:** [IEEE-CIS Fraud Detection, Kaggle](https://www.kaggle.com/competitions/ieee-fraud-detection).  
**Статус на 09.11.2026:** выполнены первичный EDA, `baseline_v1`, анализ ошибок, недельная диагностика и три expanding-window проверки внутри train. **Независимый запуск скриптов обучения и оценки на исходных локальных данных выполнен:** ROC-AUC = 0,749975, AP = 0,141819; расхождение с результатами ноутбука равно 0 при выведенной точности. Абляционный эксперимент A/B/C с признаками `identity` выполнен на трёх одинаковых временных фолдах внутри исходной train-части. Дополнительное случайное разбиение не проводилось.

## 1. Постановка задачи и гипотеза

Цель — построить простой воспроизводимый классификатор для **ранжирования онлайн-транзакций по вероятности мошенничества**. Для каждой транзакции модель возвращает оценку `P(isFraud=1 | X)` в интервале `[0, 1]`. Классификация бинарная: `isFraud=0` — обычная операция, `isFraud=1` — мошенническая.

- **Единица наблюдения:** одна транзакция, определяемая `TransactionID`.
- **Вход `X` для `baseline_v1`:** `TransactionAmt`, `ProductCD`, `card4`, `card6`, `P_emaildomain`.
- **Цель `y`:** `isFraud` из обучающей таблицы Kaggle.
- **Одно предсказание:** числовая оценка риска для одной транзакции.
- **Прикладной смысл:** приоритизация операций для дополнительной проверки; политика отказа в платеже и её экономическая оптимальность не определяются.
- **Предполагаемый момент инференса:** обработка текущей транзакции до окончательного решения о ней. Доступность всех анонимизированных признаков в этот момент не подтверждена документацией и требует отдельной проверки в реальной системе.

**Основная гипотеза H1.** Логистическая регрессия на пяти заранее выбранных транзакционных признаках обеспечивает ROC-AUC выше константного `DummyClassifier(strategy="prior")` на хронологически отложенной валидации. Возможная причина — различия распределений транзакционных характеристик между двумя классами. Критерий проверки: ROC-AUC на одном фиксированном holdout при одинаковых наблюдениях.

### Проверяемые исследовательские вопросы

1. **Временная устойчивость (проверено).** Как изменяются ROC-AUC и AP на последующих временных интервалах при фиксированном baseline и на трёх последовательных expanding-window разбиениях? Протокол и результаты — в разделе 6.
2. **Наличие `identity` (проверено).** Даёт ли добавление только индикатора наличия записи `identity` (B) улучшение относительно исходных пяти признаков (A) на одинаковых временных фолдах? Результаты — в разделе 7.
3. **Дополнительные поля `identity` (проверено).** Изменяет ли включение характеристик `DeviceType`, `id_12`, `id_15`, `id_31` качество сверх индикатора наличия записи (C против B)? Проверяются ROC-AUC, AP, Precision@1% и Recall@1% при том же протоколе.

**Дополнительный неисполненный исследовательский вопрос:** насколько отличаются оценки при случайном стратифицированном и хронологическом разбиениях? Он не входит в перечень выполненных экспериментов; случайное разбиение не используется вместо временного.

## 3. Протокол валидации и защита от утечек

Основной протокол — хронологический holdout по `TransactionDT` (относительное время в секундах, а не календарная дата):

- `train`: `TransactionDT < 12 192 853,6`, 472 432 наблюдения;
- `validation`: `TransactionDT >= 12 192 853,6`, 118 108 наблюдений;
- `max(TransactionDT на train) = 12 192 842`, `min(TransactionDT на validation) = 12 192 900`.

Временная граница выбрана по квантилю 0,8 **без использования целевой переменной**. Транзакции с одинаковым временным значением не пересекают границу разбиения. `TransactionID` и `TransactionDT` не используются как признаки baseline.

Обучаемая предобработка находится внутри `sklearn.pipeline.Pipeline`: медиана, масштабирование и словарь категорий оцениваются только при `fit` на train. Для validation используются уже обученные преобразования. Kaggle test и public leaderboard **не использовались** ни для обучения, ни для оценки.

Внутренние временные разбиения построены **только на train**, с независимым повторным обучением pipeline в каждом фолде. Метрики по неделям первоначальной validation являются диагностикой уже зафиксированной модели, **не основанием для подбора модели по holdout**.

**Основная метрика:** ROC-AUC (соответствует метрике соревнования, измеряет качество ранжирования при различных порогах).  
**Дополнительная метрика:** Average Precision, AP (важна при редком положительном классе; зависит от базовой распространённости мошенничества).  
**Прикладная диагностическая оценка:** Precision@1% и Recall@1% при фиксированной квоте проверки 1% наиболее рискованных транзакций.

**Оставшиеся риски:** анонимизированные признаки могут быть недоступны в момент авторизации; потенциальные общие сущности или повторы между временными частями не исключены; строгий group split невозможен без надёжного идентификатора сущности. Хронологический split предотвращает использование будущих строк в обучении, но сам по себе не устраняет все возможные утечки.

## 4. Зафиксированный baseline (`baseline_v1`)

Сравниваются две модели:

1. `DummyClassifier(strategy="prior", random_state=42)`, выдающий частоту положительного класса train и не использующий содержательные признаки.
2. `LogisticRegression(solver="liblinear", C=1.0, penalty="l2", max_iter=300, class_weight=None, random_state=42)`.

| Признаки | Преобразование |
|---|---|
| `TransactionAmt` | `SimpleImputer(strategy="median")` → `log1p` → `StandardScaler` |
| `ProductCD`, `card4`, `card6`, `P_emaildomain` | `SimpleImputer(strategy="constant", fill_value="__MISSING__")` → `OneHotEncoder(handle_unknown="ignore")` |

Всё перечисленное включено в `ColumnTransformer` внутри единого `Pipeline`. Модель намеренно не использует сложные ансамбли и инженерные признаки, чтобы обеспечить интерпретируемую и быстро воспроизводимую точку отсчёта. Параметры и признаки зафиксированы до первого обучения; настройка на holdout не проводилась.

## 6. Временная устойчивость baseline (эксперимент 2)

Проверка разделена на две части. **Недельная диагностика** использует предсказания одного зафиксированного baseline на шести непересекающихся недельных срезах первоначальной validation. **Expanding-window проверка** состоит из трёх последовательных временных разбиений *внутри исходной train*; в каждом фолде повторно обучается весь pipeline. Эти эксперименты не используются для подбора модели по основному holdout.

### Недельные срезы основной validation

|---|---:|---:|---:|---:|---:|
| 0 | 18 562 | 640 | 0,03448 | 0,72671 | 0,12912 |
| 1 | 21 476 | 663 | 0,03087 | 0,76046 | 0,16321 |

На всех интервалах ROC-AUC превышает 0,5. Наблюдаемый диапазон ROC-AUC составляет **0,71581–0,77205**, AP — **0,11478–0,17412**. Доля мошенничества меняется от 2,84% до 4,14%; различия AP нельзя интерпретировать без учёта этой базовой частоты. Причины снижения качества на неделе 2 не установлены.

### Три expanding-window разбиения внутри train

Обучение выполнялось на ранних 40%, 60% и 80% исходной train-части; каждый раз модель проверялась на следующем непересекающемся временном блоке примерно в 20% train-части. Для каждого фолда обучались заново и преобразования, и логистическая регрессия.

|---|---:|---:|---:|---:|---:|

## 7. Абляционный эксперимент с признаками `identity` (эксперимент 3)

**Гипотеза H2.** Дополнительные поля `identity` могут изменять качество ранжирования мошеннических транзакций при неизменной модели и протоколе временной оценки. Использованы три варианта:

- **A — `A_transaction_only`:** пять исходных транзакционных признаков (`baseline_v1`).
- **B — `B_plus_identity_status`:** A и категориальный индикатор наличия записи `identity`.
- **C — `C_plus_identity_fields`:** B и четыре категориальных поля `DeviceType`, `id_12`, `id_15`, `id_31`.

Для всех вариантов использовались три **одинаковых expanding-window разбиения внутри исходной train**, LogisticRegression с теми же гиперпараметрами и переобучение всего pipeline для каждого варианта и фолда. Внешняя validation не использовалась для сравнения A/B/C или выбора признаков. Контрольный вариант A воспроизвёл результаты временных фолдов раздела 6 с нулевым расхождением по ROC-AUC и AP при отображаемой точности.

### Результаты

| Вариант | ROC-AUC: mean ± std | AP: mean ± std | Precision@1%: mean | Recall@1%: mean |
|---|---:|---:|---:|---:|
| A — исходные признаки | 0,74953 ± 0,02117 | 0,14121 ± 0,03311 | 0,26984 | 0,06831 |
| B — A + наличие identity | 0,75065 ± 0,02117 | 0,14419 ± 0,03315 | 0,27266 | 0,06896 |
| C — B + поля identity | **0,75252 ± 0,02269** | **0,17430 ± 0,03622** | **0,37601** | **0,09566** |

Относительно A вариант B даёт среднее изменение ROC-AUC **+0,00112**, AP **+0,00297**. Вариант C относительно A: ROC-AUC **+0,00299**, AP **+0,03309**; средний Precision@1% изменяется с **26,98% до 37,60%**, Recall@1% — с **6,83% до 9,57%**.

**Результаты по временным фолдам:**

| Fold | ROC-AUC: A | ROC-AUC: B | ROC-AUC: C | AP: A | AP: B | AP: C |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 0,73466 | 0,73543 | 0,73128 | 0,13693 | 0,14039 | 0,18056 |
| 2 | 0,74017 | 0,74171 | 0,74984 | 0,11045 | 0,11310 | 0,13536 |
| 3 | 0,77377 | 0,77482 | 0,77643 | 0,17625 | 0,17906 | 0,20699 |

### Интерпретация

Рост ROC-AUC при переходе от A к C **не наблюдается на всех фолдах**: в первом фолде метрика снижается на 0,00338, во втором и третьем растёт. Поэтому прирост среднего ROC-AUC невелик и недостаточен для вывода об устойчивом улучшении ранжирования в целом. Напротив, AP, Precision@1% и Recall@1% варианта C превышают результаты A во всех трёх исследованных периодах. Это указывает на потенциальную ценность дополнительных данных для отбора высокорисковых транзакций в выбранном протоколе.

Ограничения интерпретации: (1) три временных фолда зависимы; `mean ± std` не является доверительным интервалом и статистическая значимость не оценивалась; (2) неизвестен механизм появления записи `identity` и реальная доступность полей на момент авторизации; (3) по результатам внутренних фолдов нельзя автоматически обещать прирост на ещё одном будущем периоде. Основной baseline `baseline_v1` и его исходные метрики на holdout не заменяются моделью C задним числом.

## 8. Итоговые выводы и ограничения

1. **Основная гипотеза H1 подтверждена на выбранном хронологическом holdout:** простой baseline превосходит константный метод (ROC-AUC 0,74998 против 0,50000; AP 0,14182 против 0,03441).
2. **Временная устойчивость ограничена:** ROC-AUC на внутренних фолдах 0,73466–0,77377, AP 0,11045–0,17625. Метрики различаются по периодам и распространённости мошенничества.
3. **Гипотеза H2 получила частичную поддержку:** дополнительные `identity`-поля улучшают AP и отбор top-1% на всех трёх внутренних фолдах, но небольшое среднее изменение ROC-AUC неоднородно по времени.
4. **Основные ограничения:** непроверенная доступность полей при инференсе, неполная семантика анонимизированных данных, возможная зависимость операций одной сущности, отсутствие оценки задержек разметки, калибровки и экономической стоимости ошибок. Исходный EDA охватывает выбранный, а не полный набор признаков.
5. **Следующая проверяемая гипотеза:** преимущество варианта C по AP и Precision@1% сохранится на новом, ещё не использованном при выборе признаков временном интервале при подтверждённой доступности полей на момент проверки операции. Для промышленного использования необходим отдельный протокол проверки и определение стоимости ошибок.

## 9. Локальная среда, скрипты и воспроизведение

Проект выполняется в локальном Jupyter Notebook из Anaconda. В подтверждённом локальном запуске использовались **Python 3.12.4, scikit-learn 1.4.2, pandas 2.2.2, numpy 1.26.4, matplotlib 3.8.4**. Версии остальных пакетов не фиксировались отдельно.

### Установка

В Anaconda Prompt, из каталога проекта:

```bash
conda create -n ieee-fraud-rnd python=3.12 -y
conda activate ieee-fraud-rnd
python -m pip install -r requirements.txt
jupyter notebook
```

Выполнение возможно и в существующем окружении, если необходимые зависимости установлены. Установка из `requirements.txt` может допускать диапазоны версий, кроме явно закреплённых пакетов. Для полностью идентичной среды потребуется дополнительный снимок установленных зависимостей (`pip freeze` или `conda env export`). Команды приведены для повторения процедуры; запуск в новом окружении пока не проверен.

### Структура проекта

```text
ieee-fraud-detection/
├── README.md
├── requirements.txt
├── .gitignore
├── ieee-fraud-detection.zip           # локально, не включается в Git
```

Исходные файлы CSV не распаковываются на диск: код читает необходимые колонки непосредственно из ZIP. Скрипты обучения используют только **пять признаков** исходного baseline. Присоединение `identity` требуется для исследовательской части EDA, но не для воспроизведения этой модели.

**Путь к архиву:** `ieee-fraud-detection.zip` расположен в корне проекта. Пути в `configs/baseline.json` задаются относительно текущей рабочей директории. Команды запуска следует выполнять из **корня проекта**. Для ноутбука `ARCHIVE_PATH = Path("ieee-fraud-detection.zip")` также предполагает запуск из корня.

### Запуск воспроизводимого baseline

После установки зависимостей из раздела «Установка», в Anaconda Prompt (Windows):

```bat
python -m src.train --config configs/baseline.json
python -m src.evaluate --config configs/baseline.json
```

Либо одной командой:

```bat
scripts\run_baseline.bat
```

На Linux/macOS:

```bash
bash scripts/run_baseline.sh
```

Скрипт `train.py` определяет квантильную временную границу, обучает тот же pipeline, что и ноутбук, и сохраняет `artifacts/baseline_logreg.joblib` и `artifacts/baseline_metadata.json`. Скрипт `evaluate.py` загружает сохранённую модель, формирует тот же holdout и рассчитывает ROC-AUC, AP и качество отбора top-1%. Выходные файлы — `results/baseline_metrics.csv` и `results/baseline_script_summary.json`.

**Фактический результат независимого запуска на исходных локальных данных (09.11.2026):** ROC-AUC = 0,749975 и AP = 0,141819; значения совпали с ноутбуком до выведенной точности, абсолютное расхождение по обеим метрикам — 0. Программная часть также проверена на искусственном CSV внутри ZIP. Это подтверждает воспроизводимость модели в проверенном окружении, но не заменяет повторный запуск на чистой среде и проверку Git-репозитория. В ноутбуке дополнительно зафиксированы TP=363, FP=819, FN=3701, TN=113225 при top-1%.

### Воспроизведение исследования

При запуске `IEEE_Fraud_EDA.ipynb` выполнить ячейки по порядку (`Kernel → Restart & Run All`). Отключённые по умолчанию дополнительные сканирование пропусков и bootstrap не являются условиями основного результата. В результате создаются таблицы и графики EDA, baseline и временной проверки.

В рабочем репозитории следует сохранять **точные агрегированные файлы `results/` из локального Jupyter и независимого запуска**, а не заменять их предварительно переписанными или округлёнными таблицами. Запуск `evaluate.py` рассчитывает метрики заново. Для воспроизведения опыта H2 используется самостоятельная команда `python -m src.identity_ablation --config configs/identity_ablation.json`.
